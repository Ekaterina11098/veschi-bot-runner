# Общий агент собственника VESCHI

Отдельный @veschi_owner_ai_bot отвечает на обычные текстовые вопросы собственника и допущенного наблюдателя в одной закрытой группе. Видит сохранённые источники трёх кабинетов, MPStats, МойСклад, собственную себестоимость, сохранённую экономику и Ozon. Обработчик выбирает инструменты в цикле, считает в Postgres/детерминированной арифметике и использует последние шесть завершённых диалогов группы/темы для уточнений.

## Изоляция

Добавлены только `owner_agent/**` и отдельные workflows. Существующие pins, агенты, очереди, расписания и операции кабинетов не импортируются и не изменяются. У нового агента нет инструментов записи в WB/МойСклад, управления другими агентами, свободного SQL, eval, произвольных URL и новых сборов.

`owner_agent_read` — фиксированный SECURITY INVOKER RPC, доступный только серверной роли. Источники читаются; `owner_agent_config`, `owner_agent_members`, `owner_agent_jobs`, `owner_agent_setup` хранят только настройки нового агента. RLS включён, anon/authenticated/PUBLIC доступ отозван. Серверный Supabase key остаётся широким секретом раннера: программный allowlist не заменяет ограниченную роль БД.

Метаданные группы/участников сохраняются в закрытой setup-таблице, а не в публичных логах runner. Токен нового бота хранится только в GitHub Actions secret `OWNER_TELEGRAM_BOT_TOKEN`. Edge хранит только хеш секрета вебхука в своей конфигурации. Токен и содержимое вопросов/ответов не логируются.

## Развёртывание

1. Применить `schema.sql` один раз миграцией. При первом развёртывании таблицы пустые и агент неактивен. В этом проекте схема уже применена 19.10.2026, повторно не запускать CREATE TABLE.
2. Сохранить токен **нового** бота в `OWNER_TELEGRAM_BOT_TOKEN` репозитория runner. Используются существующие `SUPABASE_URL`, `SUPABASE_SECRET_KEY`, `OPENAI_API_KEY`; остальные секреты и настройки не менять.
3. В отдельной частной группе отключить privacy у нового бота и заново добавить его. Собственник и наблюдатель отправляют сообщения. Запустить `Owner agent — identify new bot and group`. Этот workflow не подтверждает offset, не отправляет сообщения, не вызывает ИИ и не меняет вебхук. Результат — `owner_agent_setup`.
4. По результатам явно сверить группу и кто является собственником. Внести единственную конфигурацию id=1 с точными chat_id/bot_id/bot_username, active=false и разрешённые user_id с ролями owner/observer. Не включать обнаруженных посторонних автоматически.
5. Развернуть **новую** Edge Function `owner-agent-webhook`: `webhook.ts`, `ingress.mjs`, `data.mjs`. verify_jwt=false допустим, потому что обработчик проверяет секрет Telegram и собственный список доступа. Используется существующий Edge secret `GITHUB_WORKFLOW_DISPATCH_TOKEN`; его значение не менять. Запись GITHUB dispatch направлена только на новый workflow.
6. Доставить новый `owner-agent.yml` в main публичного runner. Убедиться, что проверки прошли. Только затем запустить отдельный `owner-agent-activate.yml`: проверяет идентичность нового бота, частную группу, privacy, конфигурацию, новый ingress и устанавливает только его вебхук. Старые вебхуки не затрагиваются.
7. Отправить реальный вопрос, затем уточнение. Проверить сохранённые evidence, статус done и Telegram receipt. Не объявлять запуск завершённым до фактической проверки получения ответа в группе.

Для остановки: `update public.owner_agent_config set active=false where id=1;` — новые вопросы и отправка блокируются. Остальные агенты не затрагиваются.

## Данные и ограничения первой версии

Неизвестное не0. История содержит страницы, маркеры завершения, повторы и отчёты разных периодов. Latest collected_at не означает сегодняшний период. Массивы читаются постранично; суммы считаются для одного точного снимка с сохранением пропусков. Полноту бизнес-области отдельно проверяет агент. Агрегация требует JSON чисел, числовые строки считаются неизвестными. Нет автоматической загрузки свежих данных, обновления других агентов, прогнозов и изменений бизнеса.

Модель может ошибаться в выборе периода/показателя. Проверить на реальных контрольных вопросах собственника, включая известные контрольные цифры и неполные данные. На один вопрос максимум10 раундов/16 инструментов, max_output_tokens2400, модель по умолчанию gpt-4o-mini, можно задать OWNER_AI_MODEL. В каждом запросе store=false; данные всё равно передаются провайдеру модели. Локально долговременно хранятся вопросы, ответы, метаданные evidence и квитанции в Supabase.

Ответы текстовые, файлы/голос/изображения пока не обрабатываются. Агент отвечает на каждое обычное текстовое сообщение разрешённого участника, кроме slash-команд, в закреплённой группе. Основная память — последние шесть диалогов; долговременное обучение на исправлениях пока не реализовано. GitHub Actions может добавлять задержку запуска.

Дубли dispatch отсеиваются атомарным claim. При неизвестном результате sendMessage статус uncertain; повторная отправка автоматически запрещена. Прерванный running job тоже не перехватывается автоматически. Для таких случаев требуется проверка квитанции и отдельное восстановление. Новые сообщения создают новые вопросы, старые ответы повторно не рассылаются.

## Проверки

`node --test owner_agent/test.mjs` — офлайн, без ключей/сети. Дополнительно проверены реальные SQL чтения, агрегация, пагинация и ACL/RLS. Первое discovery подтвердило идентичность нового бота и отключённый privacy; пустой успешный PostgREST ответ выявил ошибку парсинга, исправленную отдельным регрессионным тестом. Качество реального модельного ответа и доставки проверяется после регистрации группы.
