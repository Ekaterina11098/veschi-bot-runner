# WB → МойСклад: ежедневное проведение

Решение владельца от 04.11.2026: ИП, ООО и Китай запускают списания один раз в день в 19:00 Europe/Moscow. Внеплановый запуск требует нового разового подтверждения владельца. Недостаток доступного остатка блокирует отгрузку до решения владельца.

- GitHub cron `0 16 * * *` задаёт 19:00 МСК. Облачный опрос служит резервным триггером; периодический опрос не разрешает дополнительные списания.
- Для каждого кабинета атомарно создаётся одна запись `daily_execution:v1:YYYY-MM-DD`. Повторный запуск, включая повтор после ошибки, документы не создаёт. Ошибка не освобождает дневной допуск.
- При задержке планировщика ежедневный запуск принимается в течение часа 19:00–19:59 МСК. Уже разрешённый пакет завершает свои цепочки. После закрытия окна новые пакеты ждут следующего дня или подтверждения.
- Заказы, отгрузки и возвраты по одной поставке остаются отдельной связанной цепочкой. Ежедневный пакет может содержать несколько поставок.
- Внеплановый запуск: оператор сначала спрашивает владельца в чате. Только после явного ответа сохраняется приватная запись `owner_approval:v1:<id>` с `owner_confirmed: true`, точным `cabinet` (`token_1`, `token_2` или `token_3`), непустым списком `supply_ids` и временем окончания `expires_at`. Запуск получает `execution_kind=manual` и `owner_approval_id=<id>`. Один допуск разрешает только эти поставки и расходуется атомарно. Самостоятельно выставлять подтверждение запрещено.
- Неподтверждённый ручной запуск сохраняет `owner_approval_request:v1` и возвращает `owner_approval_required` без проведения документов. Оператор сообщает запрос владельцу. Недостаток остатков сохраняется в `stock_approval_request:v1`; пополнение или иное решение не отменяет необходимость свежей проверки остатков.
- Предпросмотр, чтение и проверка статуса доступны независимо от времени. Ozon продолжает работать по своему прежнему расписанию.

Проверки: новое расписание, повтор в тот же день, граница следующего дня, прямой вызов обработчика, истёкшее/повторно использованное подтверждение, ограничение точным списком поставок и нехватка остатков покрыты тестами `test_fbs_daily_schedule.py`. Проверки повторов API, сохранения связей и облачного таймера проходят.

До изменения уже падал старый тест `test_221_raw_with_one_cancelled_is_220_picked` в `test_fbs_matching.py`: он ожидает 220 вместо 221 при отмене после передачи продавцом. Это существующее расхождение теста с более поздним правилом сохранения переданного заказа. Состав поставок и это правило в данной задаче не менялись.
