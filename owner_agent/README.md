# Общий агент собственника VESCHI

Отдельный @veschi_owner_ai_bot отвечает на обычные текстовые вопросы собственника и допущенного наблюдателя в одной закрытой группе. Видит сохранённые источники трёх кабинетов, MPStats, МойСклад, собственную себестоимость, сохранённую экономику и Ozon. Обработчик выбирает инструменты в цикле, считает в Postgres/детерминированной арифметике и сохраняет полный доступный текстовый архив группы и ищет в нём старые договорённости и исправления.

## Изоляция

Добавлены только `owner_agent/**` и отдельные workflows. Существующие pins, агенты, очереди, расписания и операции кабинетов не импортируются и не изменяются. У нового агента нет инструментов записи в WB/МойСклад, управления другими агентами, свободного SQL, eval, произвольных URL. Разрешён точечный добор MPStats через отдельный инструмент общего агента.

`owner_agent_read` — фиксированный SECURITY INVOKER RPC, доступный только серверной роли. Источники читаются; `owner_agent_config`, `owner_agent_members`, `owner_agent_jobs`, `owner_agent_setup` хранят только настройки нового агента. RLS включён, anon/authenticated/PUBLIC доступ отозван. Серверный Supabase key остаётся широким секретом раннера: программный allowlist не заменяет ограниченную роль БД.

Метаданные группы/участников сохраняются в закрытой setup-таблице, а не в публичных логах runner. Токен нового бота хранится только в GitHub Actions secret `OWNER_TELEGRAM_BOT_TOKEN`. Edge хранит только хеш секрета вебхука в своей конфигурации. Токен и содержимое вопросов/ответов не логируются.

## Развёртывание

1. Применить `schema.sql` один раз миграцией. При первом развёртывании таблицы пустые и агент неактивен. В этом проекте схема уже применена 19.10.2026, повторно не запускать CREATE TABLE.
2. Сохранить токен **нового** бота в `OWNER_TELEGRAM_BOT_TOKEN` репозитория runner. Используются существующие `SUPABASE_URL`, `SUPABASE_SECRET_KEY`, `OPENAI_API_KEY`; остальные секреты и настройки не менять.
3. В отдельной частной группе отключить privacy у нового бота и заново добавить его. Собственник и наблюдатель отправляют сообщения. Запустить `Owner agent — identify new bot and group`. Этот workflow не подтверждает offset, не отправляет сообщения, не вызывает ИИ и не меняет вебхук. Результат — `owner_agent_setup`.
4. По результатам явно сверить группу и кто является собственником. Внести единственную конфигурацию id=1 с точными chat_id/bot_id/bot_username, active=false и разрешённые user_id с ролями owner/observer. Не включать обнаруженных посторонних автоматически.
5. Развернуть **новую** Edge Function `owner-agent-webhook`: `webhook.ts`, `ingress.mjs`, `data.mjs`. verify_jwt=false допустим, потому что обработчик проверяет секрет Telegram и собственный список доступа. Используется существующий Edge secret `GITHUB_WORKFLOW_DISPATCH_TOKEN`; его значение не менять. Запись GITHUB dispatch направлена только на новый workflow.
6. Доставить новый `owner-agent.yml` в main публичного runner. Убедиться, что проверки прошли. Только затем запустить отдельный `owner-agent-activate.yml`: проверяет идентичность нового бота, частную группу, privacy, конфигурацию, новый ingress и устанавливает только его вебхук. Старые вебхуки не затрагиваются.
7. Отправить реальный вопрос, затем уточнение. Проверить сохранённые evidence, статус done и Telegram receipt. Не объявлять запуск завершённым до фактической проверки получения ответа в группе.

Для остановки: `update public.owner_agent_config set active=false where id=1;` — новые вопросы и отправка блокируются. Остальные агенты не затрагиваются.

## Данные и ограничения первой версии

Неизвестное не0. История содержит страницы, маркеры завершения, повторы и отчёты разных периодов. Latest collected_at не означает сегодняшний период. Массивы читаются постранично; суммы считаются для одного точного снимка с сохранением пропусков. Полноту бизнес-области отдельно проверяет агент. Агрегация требует JSON чисел, числовые строки считаются неизвестными. Нет автоматической загрузки свежих данных, обновления других агентов, прогнозов и изменений бизнеса.

Модель может ошибаться в выборе периода/показателя. Проверить на реальных контрольных вопросах собственника, включая известные контрольные цифры и неполные данные. На один вопрос максимум18 раундов/16 инструментов и8 минут до очередного раунда, max_output_tokens2400, модель по умолчанию gpt-4.1-mini, можно задать OWNER_AI_MODEL. В каждом запросе store=false; данные всё равно передаются провайдеру модели. Локально долговременно хранятся вопросы, ответы, метаданные evidence и квитанции в Supabase. Каталог по умолчанию исключает архивные replay_*, они доступны явным поиском replay.

Ответы текстовые, файлы/голос/изображения пока не обрабатываются. Агент отвечает на каждое обычное текстовое сообщение разрешённого участника, кроме slash-команд, в закреплённой группе. Основная память — последние шесть диалогов; долговременное обучение на исправлениях пока не реализовано. GitHub Actions может добавлять задержку запуска.

Дубли dispatch отсеиваются атомарным claim. При неизвестном результате sendMessage статус uncertain; повторная отправка автоматически запрещена. Прерванный running job тоже не перехватывается автоматически. Для таких случаев требуется проверка квитанции и отдельное восстановление. Новые сообщения создают новые вопросы, старые ответы повторно не рассылаются.

## Проверки

`node --test owner_agent/test.mjs` — офлайн, без ключей/сети. Дополнительно проверены реальные SQL чтения, агрегация, пагинация и ACL/RLS. Первое discovery подтвердило идентичность нового бота и отключённый privacy; пустой успешный PostgREST ответ выявил ошибку парсинга, исправленную отдельным регрессионным тестом. Качество реального модельного ответа и доставки проверяется после регистрации группы.

Контрольные значения получены отдельными SELECT напрямую по исходным снимкам/таблицам, не от модели. Результаты, вопросы и evidence хранятся приватно в owner_agent_setup.acceptance/acceptance_history; эталоны не передаются модели.

Итог: 9 сценариев проходят после исправлений; 24 офлайн-проверки проходят. Проверены записи заказов по трём кабинетам за11.09–10.10.2026, последовательные уточнения по отменам ИП/Китай/ООО, неотменённые в последнем кабинете, отсутствие точной прибыли за незавершённый день, разные даты покрытия рекламных отчётов MPStats и чтение двух сохранённых net_profit для разных SKU/кабинетов/периодов. Сохранённый net_profit не является независимым аудитом финансовой формулы или первичных расходов.

Исправлены путаница человеческого названия источника с точным ID, переключение WB→Ozon в уточнении, нули при отсутствующем JSON-пути, поиск сохранённой экономики в диагностических снимках, ложное распознавание календарной даты как финансовой суммы. Добавлен детерминированный order_snapshot_counts, выбирающий ровно один последний завершённый снимок точного периода на кабинет. Это контрольный набор, не гарантия правильности произвольного вопроса. История больше не ограничена шестью диалогами: см. раздел долговременной памяти ниже. Выгрузки остаются разной полноты/свежести; исторические контрольные числа не объявляются текущими продажами.

## Долговременная память

Аддитивная миграция memory.sql (применена 19.10.2026) добавляет закрытый owner_agent_messages и invoker RPC owner_agent_history. Оригиналы не удаляются при сокращении контекста. Все уже сохранённые вопросы и подтверждённые ответы перенесены. Триггер архивирует новые вопросы и каждую подтверждённую часть ответа. Ingress сохраняет тексты/подписи допущенных участников, команды и версии edited_message. Правка не запускает повторный ответ. Метаданные включают автора, время, тему и ссылку на исходное сообщение. При поиске возвращается последняя редакция, оригиналы остаются для аудита.

Каждый запрос получает 20 последних сообщений, до30 выделенных поправок и до20 совпадений с вопросом. Это только начальная подборка: инструмент group_history ищет по всему архиву, возвращает total/has_more/next_offset и позволяет читать следующие страницы, старые темы, исходное сообщение и ответы. Полные тексты не заменяются модельным резюме. Автоматическая отметка поправки — подсказка для поиска, не семантическая гарантия. Поздняя применимая человеческая поправка приоритетнее старой версии и ответа агента; неоднозначные конфликты нужно уточнять. Старые финансовые цифры не становятся актуальными фактами.

RPC привязан к единственной активной группе в конфигурации; модель не выбирает chat_id. RLS и отсутствие прав anon/authenticated защищают архив. Из памяти нельзя получить новые права или изменить инструменты/правила расчёта. Память действует между перезапусками раннера.

Telegram Bot API не отдаёт историю до подключения бота, уведомления об удалении обычных сообщений и содержимое вложений. Сохраняются доступные тексты и подписи, а не распознанные голосовые/картинки. Старую переписку до подключения можно отдельно импортировать из экспорта Telegram. Текущий начальный архив — с первого сохранённого сообщения19.10.2026. Доступны только сообщения допущенных участников, доставленные Telegram вебхуку. Включены обновления message и edited_message; pending updates при обновлении вебхука не сбрасываются.

Проверки памяти: node --test owner_agent/test.mjs; отдельный workflow owner-agent-memory.yml использует реальную модель и синтетическую переписку вне рабочей памяти, не отправляет сообщения в Telegram. Проверены старое соглашение после40 промежуточных сообщений, более поздняя человеческая поправка вопреки ошибке агента и исправленная версия сообщения. Поиск/изоляция/последняя редакция проверены отдельно в Postgres с rollback.

## Добор из MPStats —19.10.2026

По явному запросу пользователя добавлен mpstats_products: при отсутствии точного проверенного периода агент добирает товарный отчёт из MPStats, сохраняет owner_mpstats_products и повторно читает результат. Существующий mpstats_products_validated переиспользуется без повторного запроса. Источник, даты и кабинет проверяются; все страницы выданного каталога собираются и нормализуются неизменённым модулем частного источника, закреплённым только для этого общего агента на29f6e3f4a59e87c43a085f18d69f8509fe1cf6c1. Чужие pins и файлы не меняются.

Общий агент использует тот же mutex bot-mpstats-data, учитывает сохранённый общий cooldown и сохраняет Retry-After. Выбор кабинета MPStats проверяется до/после каждой страницы и восстанавливается после чтения. Даты только завершённые, окно до31дня, до6 недостающих отчётов за диалог; один отчёт не более1500 товарных записей/5MB. Лимиты провайдера и неготовность явно возвращаются как пробел, не ноль. Нет вызовов WB и торговых изменений.

Текущее стандартное окно —7 завершённых дней до вчера по Москве. Первое чтение при запросе последнего/актуального периода программно привязано к этому окну. Для ухудшения нужен предыдущий сопоставимый период; старая дата загрузки/выгрузка WB не заменяет актуальную статистику MPStats. Отсутствие собственной прибыли не блокирует анализ подтверждённых продаж. Прибыль/валюта не объявляются проверенными автоматически.

Новый invoker RPC owner_agent_mpstats_products доступен только service_role. Итоги считаются по полному выданному каталогу, а products — страница; orders, orders_count, sales_count, returns_count различаются. Полнота выданного каталога не доказывает наличие исключённых карточек, for_pay не является собственной чистой прибылью. Ранее описанное ограничение запроса только сохранённых данных заменено этим разрешённым добором.

При актуальном сравнении текущие и предыдущие равные периоды сначала программно читаются/добираются одинаково для всех нужных кабинетов, затем передаются модели. Финальная проверка отклоняет ответ с пропущенными датами и неподтверждёнными выводами о прибыли; модель не может незаметно переключить кабинет на другую неделю. Это дополнительно проверяется реальным вопросом собственника с проверкой покрытия всех6 пар кабинет/период.

Числовое сопоставление общего актуального сравнения выполняется программой: точный кабинет, текущий/предыдущий период, абсолютное изменение, процент только при ненулевой базе. Модель получает короткую рассчитанную сводку и пишет план дальнейшей проверки без чисел; направления изменений тоже выводит программа; таблицу дат и фактов добавляет программа. Выдуманный малый знаменатель вместо нуля запрещён. Денежные выплаты не подставляются в собственную прибыль. Более детальные вопросы по товарам/причинам идут через обычный цикл инструментов.
